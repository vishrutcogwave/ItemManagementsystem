# IMS automation and reconciliation report

Run date 19 November 2026, Asia/Kolkata. Working tree based on commit `117a5df`.

## Execution and readiness

The frontend and Spring Boot backend were executed on loopback with a fresh PostgreSQL 14 database. Flyway validated and applied all 13 migrations. A temporary platform administrator used the first-login password change flow. The test store, users, master records and transactions were created through IMS. Independent verification used a read-only JDBC connection.

| Backend JUnit unit and integration | 179 | 179 | 0 | 0 |
| Playwright browser, API and SQL assertions | 51 | 51 | 0 | 0 |

JUnit and Playwright are separate executions with overlapping coverage. Hardware and other unverified scenarios listed below are outside these totals. The working tree passes the executed regression suites. Release sign-off still requires the unverified coverage below and representative business data.

No production services, production database, deployment, commit or push were used. Existing working-tree changes were retained. The starting changes included sale payment DTOs and V13, POS and Bill Modification screens, Payment Summary, invoice formatting and native raster bridge support.

## Billing, API, database and authorization

- The payment API progressed from Cash to UPI, Card, two-way split and three-way split. It rejected zero, negative and excessive amounts, and a repeated revision returned HTTP 409. The browser added and removed rows, confirmed a corrected split and reopened the bill. SQL verified the current payment JSON and four initial audit revisions with editor and timestamp. Concurrent bill writes were exercised by the Java suite.
- The genuine browser POS checkout rejected an overpayment, saved a partial Cash and UPI sale and reconciled its payment rows with PostgreSQL. The controlled sale produced exactly one stock-out movement for two units.
- The supplier payment replay returned the same payment. PostgreSQL recorded one allocation of ₹30. The outstanding balance reconciled to ₹75.
- The browser verified login and logout, category creation and search, 390 px Payment Summary layout, and navigation across 17 screens. The Java suite exercised catalog and barcode operations, imports, sales, purchase and transfer state changes, supplier settlement, security, tenants, branches, audit rollback, subscriptions and printing APIs.
- The staff account received HTTP 403 on Payment Summary and bill modification APIs. Anonymous API access returned HTTP 401. The final browser run produced no uncaught page errors. Expected logged-out session checks returned HTTP 401.

## Defects reproduced and corrected

| Finding | Before | Fix and verification |
|---|---|---|
| Supplier ledger ignored the branch selection | An empty branch returned two rows and a ₹75 closing balance. | The API now accepts the branch and scopes both purchase debits and payment allocations. Empty-branch API, browser, and Java regressions verify zero rows and zero balances. |
| Historical stock showed the present balance | An empty January 2000 window showed a closing quantity of 11 after later transactions. | The closing balance now removes net movements after the selected date. Historical and current-period API regressions verify the calculation. Inventory value uses the current weighted average cost, explicitly identified in the browser. |
| PDF used Letter for A4, A5 and custom | Chromium ignored the malformed CSS size property. | The shared invoice template now emits a valid page size. PDF geometry and both entry points were verified. |
| Dialogs had no accessible name | The bill confirmation and category dialogs could not be located by accessible name. | Shared modal title and description are associated with the dialog through ARIA. Both real browser workflows passed after the change. |
| Default report dates started a day early | In Asia/Kolkata the November default started on 31 October. | Date input values now use the local date and its full timezone offset. The browser checks the first day of the current month. |
| Sales PDF lost the rupee symbol | The report exporter’s Helvetica font did not support ₹. | PDF text uses the supported INR label. The downloaded PDF is checked for the verified INR 105.00 total. |
| README listed demo credentials that did not work on a fresh installation | Login returned HTTP 401 because startup does not invoke the legacy demo seeder. | The README now documents explicit administrator provisioning and disposable QA setup. The existing startup security behavior was preserved. |

The first complete run on the final backend sources recorded 179 cases, with 169 passing and all 10 Supplier Payment cases failing to initialize after an embedded PostgreSQL 10-second startup timeout. A serial rerun with the browser QA services stopped and the Spring test-context cache limited to four is recorded in the execution table above.

The earlier browser failures were investigated and rerun. CSSOM canonicalizes portrait A4 and A5 to `a4` and `a5`. The assertion accounts for that browser serialization and independently checks the actual PDF dimensions.

## Coverage remaining

- Physical printer connectivity, paper output, feeding, cutting and hardware compatibility were not tested. The software bridge test used a mock, with no hardware dispatch or live Windows or Android bridge testing in this run.
- The PDF sample establishes one-page geometry and consistency. Multi-page invoices, logo rendering, the invoice modal’s separate PDF download button, every custom size and every printer-driver margin were not verified.
- Navigation was covered across the listed modules. Every browser CRUD action, filter combination, export format, validation branch, loading state and failure simulation was not exercised. The browser was Chromium only. Production data and capacity were not assessed.
- Report checks used controlled transactions and selected metrics. Further cases include supplier bills partially paid at purchase time, cancellation and settlement edge cases, high-volume sorting, and reconciliation against independently prepared production-like datasets.
- Historical stock quantities are now as of the selected day. Historic weighted costs are unavailable in the movement ledger. The valuation is an estimate using present weighted cost.
